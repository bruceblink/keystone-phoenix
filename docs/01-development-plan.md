# Keystone Phoenix 开发计划

鉴权与授权统一架构见 [`08-auth-authorization-parity-architecture.md`](08-auth-authorization-parity-architecture.md)。本文件同时记录 Phoenix 本地执行顺序和与 Keystone Native 的跨项目验收要求。

## 1.0 发布目标与后续维护

目标是先完成 Native、Phoenix 和 admin-web 的 1.0 功能及发布验收。1.0 范围内，同一份 admin-web 对两套后端的已支持功能应具有一致的接口和可见行为；Phoenix LiveView 以 admin-web 为页面和交互基准。Native 1.0 发布后停止新增业务功能，继续修复缺陷、安全问题和依赖兼容问题；后续新功能主要由 Phoenix 开发。1.0 的共享接口仍须保持兼容，新功能是否由 Native 实现不再默认要求一致。

当前主体功能已有实现及多轮真实数据库和浏览器检查，但还不能发布 1.0。当前开发分支中 Phoenix 版本为 `0.3.0`，Native 为 `0.1.0-SNAPSHOT`，admin-web 为 `0.1.0`；这些版本号不是完成百分比。1.0 的主要剩余工作如下：

1. 完成双后端的接口、权限和业务错误差异核查，保持既有 HTTP 状态。已知 API Key 全部授权范围失效时 Phoenix 返回 401，Native 返回 403；这项差异需要在不违反状态兼容要求的前提下决定处理方式。用户名查询的 Unicode 匹配也未完全一致。所有业务错误应有可反查的唯一代码，目前仍有通用代码覆盖多个原因。
2. 按页面逐项验证新增、编辑、删除、筛选、分页、错误和重试，覆盖只读及不同操作权限。admin-web 分别连接两套后端，LiveView 另做同等操作和布局检查。LiveView 监控页已补齐单项失败和重试；其他页面仍有权限入口和闭环待核对。
3. 固定 1.0 候选提交、版本、接口目录、数据库迁移和前端构建产物，在隔离环境完成全新安装、旧库升级、备份恢复及同一构建的双后端切换。两后端正式镜像、前端发布产物和校验信息必须与候选提交一致。当前 admin-web 仓库只有 CI 工作流，正式产物的生成与发布流程仍需明确并验证。Native 当前发布流程只公布镜像且只检查健康接口；须明确是否另发 Release 和二进制，并用正式候选 Native 镜像及真实 MySQL 验证登录、授权和 API Key 等主要业务。
4. 对实际计划启用的部署能力完成安全和运行验收，包括认证、授权、代理、日志脱敏和故障恢复。部署说明须明确数据库和文件持久化、备份恢复、密钥和 HTTPS 配置。真实身份提供方、硬件 Passkey、多节点恢复和生产代理链目前缺少完整证据；是否作为 1.0 必需项取决于正式部署是否启用这些能力。当前 Native 任务锁属于单进程锁，不能据此声明多节点调度安全；若 1.0 只支持单节点，应在支持范围中写明。未验收的能力不能标为支持。

尚未完成逐页和逐接口清单，不能可靠换算完成百分比或承诺发布日期。先完成差异清单并按上述四项给每项记录剩余工作、负责人和验收结果，再估算发布工期；不得用单次通过的测试数量代替完整发布验收。若发布验收失败，分别回退应用版本或恢复已验证的数据库备份，不修改已发布的迁移。

## 当前执行：按账号能力显示导航和读取监控

1. Native 和 Phoenix 增加同一路径的当前人类会话能力查询。返回当前有效权限和各资源的数据范围是否允许列表入口；不返回部门明细，不依赖权限版本缓存。拒绝 API Key，查询失败时返回原有授权错误。已有业务接口继续逐次鉴权。
2. admin-web 根据两端能力结果控制导航和路由，保留有权访问的原目标；无可访问页面或能力读取失败时提供明确提示和重试。Phoenix LiveView 同步核对普通账号的入口及操作权限。
3. admin-web 将监控数据分项读取，单项失败时保留其他可读取资源；权限拒绝不得显示为模拟数据。各项重试和原有敏感操作验证保持独立。
4. 验收使用独立 MySQL、PostgreSQL 和 Codex 内置浏览器，覆盖多角色、数据范围、无权限、权限变更、依赖失败、低权限登录及部分监控可用。两端分别执行定向接口测试，前端执行定向测试、全量测试和生产构建。

### 阶段一：公共接口和 UUID 主键冻结

- 固定 Principal、凭据类型、认证强度、权限版本和错误分类。
- 固定权限目录、权限 UUIDv5 向量和 `resource:action` 约定。
- 用户、角色、部门、菜单、权限、会话、令牌族、API Key、MFA 请求和安全事件统一使用 UUID。
- 新业务实体使用 UUIDv7；权限目录和固定种子使用固定命名空间的 UUIDv5。
- 外部接口使用规范小写连字符 UUID 字符串。Native 的 MySQL 使用 `BINARY(16)`；写入和按 ID 过滤使用参数侧 `UUID_TO_BIN(?, 0)`，文本结果使用 `BIN_TO_UUID(id, 0)`，不得在过滤列上调用 `BIN_TO_UUID`。Phoenix 的 PostgreSQL 使用原生 `uuid` 类型。
- 删除整数主键、整数外键、整数路径参数和整数兼容转换。

验收必须覆盖 UUIDv7 生成、固定 UUIDv5 测试向量、MySQL 二进制往返、索引可用性、非法 UUID、空值、全量主键/外键类型检查和重复迁移。旧整数输入必须拒绝，不提供兼容转换。

新系统固定使用 `ALL`、`TENANT`、`SELF`、`DEPARTMENT`、`DEPARTMENT_AND_CHILDREN`、`CUSTOM`、`OWNER` 和 `MEMBER` 八种数据范围。每个资源必须登记支持的范围；未登记的范围和缺少 `tenant_id` 的请求默认拒绝。错误码由集中目录登记，并按业务条件唯一反查；HTTP 状态码保持现有接口约定。新增入口使用 `authentication_required`、`invalid_credential`、`mfa_required`、`mfa_challenge_invalid`、`mfa_step_up_required`、`active_session_conflict`、`permission_denied`、`data_scope_denied`、`session_revoked`、`resource_not_found`、`resource_conflict`、`rate_limited`、`precondition_required`、`payload_too_large`、`validation_failed`、`service_unavailable`、`authorization_unavailable` 和 `internal_error`；旧兼容代码必须记录迁移范围。

当前 `authorization_unavailable` 仅保留在 HTTPS、旧限流、JWK/Passkey/OIDC、任务与监控服务、个人资料/用户认证会话及 API Key 授权服务的旧边界映射。迁移时保持原 HTTP 状态，只替换边界错误码；领域层的内部原子错误名不作为外部错误码。

### 阶段二：收紧角色授权

- 管理员能力必须从系统角色和权限目录读取。
- 删除 `is_admin` 和无角色管理员旁路；没有角色权限的主体必须拒绝。
- HTTP、LiveView、领域命令和 Native REST 拦截器使用同一决策结果。
- 缺少权限、范围越界、主体无效和策略存储不可用时默认拒绝。

### 阶段五：资源范围矩阵
